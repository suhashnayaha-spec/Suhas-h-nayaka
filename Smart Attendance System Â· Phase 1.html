    Data structures behind it

    Each part of the workflow uses the structure that suits it best. The demo above runs on real implementations of the first three.

    Hash table

    Maps a USN to a student record, so lookup takes O(1) on average. The result message above shows which bucket was checked.

    Queue

    Check-in requests are processed in arrival order (FIFO). The queue is temporary; the log is the record.

    List

    Attendance entries are kept in order and traversed to build the log and the percentage report in O(n).

    Tree

    Institute → department → semester → section → student, so classes can be grouped and traversed.

    How a record is saved

    Every entry passes the same checks before it is stored.

    Sign inTeacher is verified for their role.
    Pick sessionCourse, section and date.
    Find studentHash lookup by USN.
    Check duplicateOne entry per student per session.
    SaveStatus, timestamp and who marked it.
    ReportTotals and percentage update.

    Teachers

    Create sessions, mark attendance and review class reports.

    Students

    See only their own attendance history and percentage.

    Administrators

    Manage users, classes and settings, with an audit trail for corrections.

    Planned stack: React.js frontend, Python Flask API, PostgreSQL with a unique constraint on (session_id, student_id). Face verification is an optional later extension that would need consent and approval.

    Phase 1 project report

    Data Structures (LA-2, CSE201) · Batch 5. A condensed version of the full report.

    Abstract

    Most colleges still record attendance by roll call or paper sheets, which wastes teaching time, invites proxy attendance and leaves records to be retyped into spreadsheets. This project proposes a Smart Attendance System built around efficient data handling: a hash table for constant-time average lookup of student IDs, arrays for time-ordered attendance logs, and a web dashboard where teachers mark attendance, administrators see analytics, and alerts fire when a student drops below the required percentage.

    Objectives and measures of success

    No.ObjectiveMeasure of success
    O1Verify a student ID using a hash tableO(1) average lookup; 1,000 lookups in well under a second
    O2Store daily attendance as time-ordered arraysEvery record has student, class, date and timestamp, in order
    O3Reduce time spent taking attendanceA class of 60 marked in under 1 minute
    O4Generate attendance percentage reportsPer-student and per-class reports with correct figures
    O5Alert on low attendanceStudents below 75% flagged after each update
    O6Prevent duplicate markingA student cannot be marked twice in one session
    O7Role-based accessTeachers, students and administrators see only what their role allows

    How existing approaches compare

    ApproachStrengthsWeaknesses
    Manual roll call or paper registerNo cost, no technologySlow, error-prone, easy to proxy, must be retyped
    RFID or ID cardFast, easy to automateCards can be handed to a friend; readers cost money
    Biometric (fingerprint)Hard to fakeDedicated hardware, queues, hygiene concerns
    Face recognitionContactless, hard to proxyNeeds cameras, ML and careful privacy handling
    QR code or app check-inCheap, quick, uses phonesCode can be shared remotely
    Smart Attendance SystemFast lookup, structured logs, real-time analytics, ID method can be swapped laterInitial version relies on a typed or scanned ID; biometrics are future work

    The gap: most systems focus on how a student is identified, and far fewer on what happens to the data afterwards. This project is software-first and identification-method-agnostic, so it works with a typed ID, a scanned card number or a QR payload.

    Complexity summary

    OperationStructureAverageWorst case
    Verify student IDHash tableO(1)O(n) with many collisions
    Register studentHash tableO(1) amortisedO(n) during resize
    Append attendance recordArrayO(1) amortisedO(n) on array growth
    Check duplicate in a sessionHash set of IDs per sessionO(1)O(n)
    Update percentageCounter hash tableO(1)O(n)
    Class reportScan of student listO(n)O(n)

    Collisions use separate chaining and the table doubles when the load factor passes about 0.75, which keeps chains short. A per-course counter table avoids rescanning every log whenever a percentage is needed.

    Planned API

    MethodEndpointPurpose
    POST/studentsRegister a student
    GET/students/{id}Look up a student (hash table)
    POST/sessionsOpen a class session
    POST/sessions/{id}/attendanceMark attendance for a student ID
    GET/students/{id}/attendanceStudent percentage per course
    GET/courses/{id}/reportClass report
    GET/alertsStudents below threshold

    Six entities: Student, Teacher, Course, Enrollment, Session and AttendanceRecord. Enrollment resolves the many-to-many link between students and courses; AttendanceRecord links students to sessions. Prototype storage is SQLite, moving to PostgreSQL if scaled.

    Risks and limitations

    RiskMitigation
    A member is unavailableCross-train; keep tasks in the shared repository
    Scope grows (face recognition)Keep recognition as optional future work; finish the core first
    Front end and back end do not integrateAgree the API contract early; integrate weekly
    Data lossCommit often; back up the database file
    Poor performance with large dataUse the hash table and counters; test with 10,000 records

    Attendance data is personal data. The system collects only what is needed, restricts access by role, stores passwords only as hashes, and would require explicit consent and a retention policy if face recognition or biometrics are added. The first version reduces, but does not eliminate, proxy attendance. Future scope: RFID or QR scanning, face recognition, mobile apps, parent notifications and at-risk analytics.
